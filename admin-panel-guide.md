# Гайд по разработке админ-панели — dombyra.kz

Задача: дать клиенту (не разработчику) возможность самостоятельно редактировать статьи (articles.html/guide.html) и карточки каталога (catalog.html) без обращения к программисту при каждой правке.

Дата: 26.08.2026

---

## 0. Контекст текущего состояния сайта

Прежде чем проектировать админку, важно зафиксировать, откуда стартуем:

- Сейчас **все статьи и товары — это статичный HTML**, захардкоженный прямо в файлы (`catalog.html`, `articles.html`). Каждая карточка товара — это скопированный `<div>` с картинкой, названием, описанием, ценой и ссылкой на WhatsApp.
- В `README.md` уже заложен план перехода на **PHP** (`index.php`, `catalog.php`, `includes/` — модульная архитектура). Значит, бэкенд на PHP — не новое решение, а продолжение изначального замысла проекта.
- Каталог не имеет корзины и оформления заказа — вся "покупка" сводится к клику по кнопке, которая открывает WhatsApp с предзаполненным текстом. Это упрощает задачу: админке не нужна логика заказов/оплаты, только управление контентом карточек.

Исходя из этого, ниже — решение, которое **встраивается в уже существующий PHP-путь**, а не предлагает сменить стек на что-то незнакомое команде.

---

## 1. Выбор архитектуры

### Вариант А — Простая самописная админка на PHP + SQLite (рекомендуется)

**Почему подходит именно этому проекту:**
- Не требует отдельного сервера БД (SQLite — это один файл), что упрощает хостинг и бэкапы.
- Логично продолжает архитектуру, уже заложенную в README (`includes/`, модульность).
- Полный контроль над HTML-выводом — можно точно воспроизвести текущий дизайн (Tailwind-классы, стеклянные карточки и т.д.) без ограничений чужой CMS.
- Дешевле в поддержке, чем headless CMS с подпиской.

**Минусы:** всё придётся написать самим — форму логина, CRUD-формы, загрузку картинок, защиту от взлома. Это 1–2 недели работы для одного разработчика, а не "включил и готово".

### Вариант Б — Headless CMS (например, самостоятельно захостить Strapi, либо облачный вариант вроде Sanity/Contentful)

**Плюсы:** готовая админ-панель "из коробки" — логин, роли, загрузка медиа, история изменений уже есть, не нужно писать самим.
**Минусы:**
- Нужно поднимать отдельный сервис (Node.js для Strapi) — усложняет хостинг по сравнению с "просто PHP".
- Сайт должен научиться забирать данные через API (fetch) и вставлять в те же Tailwind-карточки — фактически дублирует часть текущей верстки в шаблонизацию.
- Облачные варианты (Sanity, Contentful) обычно на английском интерфейсе и с лимитами на бесплатном тарифе — надо проверить, комфортно ли клиенту.

**Когда выбирать:** если в будущем планируется больше контентных типов (не только статьи и каталог), несколько авторов с разными правами, или мобильное приложение поверх того же контента.

### Вариант В — Просто улучшенный workflow без "админки" (не рекомендуется, но дешевле всего)
Например, хранить статьи/товары в JSON-файле, который клиент правит через простой веб-редактор без БД вообще. Плохо масштабируется, легко сломать формат вручную, нет контроля доступа. Годится только как временное решение на 1–2 месяца.

**Рекомендация для этого проекта: Вариант А.** Дальше гайд построен именно на нём.

## 2. Модель данных

### Таблица `articles`
| Поле | Тип | Комментарий |
|---|---|---|
| id | INTEGER PK | |
| slug | TEXT UNIQUE | часть URL, напр. `guide` → `guide.html` |
| title | TEXT | заголовок, используется и в `<title>`, и в H1 |
| meta_description | TEXT | для SEO |
| lead_paragraph | TEXT | подзаголовок под H1 |
| cover_image | TEXT | путь к обложке |
| body_html | TEXT | тело статьи (см. пункт 3 про редактор) |
| author_name | TEXT | для JSON-LD и цитаты в конце статьи |
| published_at | DATE | |
| updated_at | DATE | важно для `dateModified` в schema — см. предыдущий SEO-гайд |
| status | TEXT | `draft` / `published` |

### Таблица `products`
| Поле | Тип | Комментарий |
|---|---|---|
| id | INTEGER PK | |
| name | TEXT | напр. "Бастау" |
| slug | TEXT UNIQUE | для якорей/URL типа `catalog.html#bastau` |
| description | TEXT | короткое описание карточки |
| image | TEXT | путь к фото |
| price | INTEGER, nullable | некоторые товары сейчас без цены ("Заказать" без суммы) — сохранить эту возможность |
| price_label | TEXT | напр. "Цена от" — часть текущего дизайна |
| whatsapp_text | TEXT | текст, который подставляется в ссылку WhatsApp |
| sort_order | INTEGER | ручная сортировка карточек в сетке |
| status | TEXT | `active` / `hidden` |
| sku | TEXT | понадобится для `Product` JSON-LD (см. SEO-гайд, пункт 4) |

## 3. Что должно быть в интерфейсе редактирования

### Для статей
- Форма с полями: заголовок, meta description, лид-абзац, обложка (загрузка файла), автор, статус (черновик/опубликовано).
- **Редактор тела статьи** — не голый `<textarea>` с HTML, а WYSIWYG (например, TinyMCE или Quill — оба бесплатные, легко встраиваются в PHP-форму через JS). Клиент не должен писать HTML-теги руками.
- Важно ограничить набор стилей в редакторе до тех, что реально поддерживает дизайн статьи (заголовки H2, списки, цитаты, жирный/курсив) — иначе клиент случайно сломает вёрстку произвольным форматированием.
- Предпросмотр перед публикацией — кнопка "Посмотреть как будет выглядеть", открывающая страницу в реальном шаблоне сайта.

### Для каталога
- Таблица всех товаров с превью-картинкой, названием, ценой, статусом — с возможностью drag-and-drop сортировки (`sort_order`) или простыми кнопками "вверх/вниз", раз карточки идут в сетке по порядку.
- Форма редактирования одного товара: название, описание (обычный textarea, длинный HTML тут не нужен — описания короткие), цена (с чекбоксом "показывать цену" / "только кнопка Заказать" — учитывая, что часть товаров сейчас без цены), фото, текст для WhatsApp-сообщения.
- Кнопка "Скрыть с сайта" вместо жёсткого удаления — чтобы можно было снять товар с продажи, не теряя данные.

## 4. Как это стыкуется с уже сделанными SEO/AEO-рекомендациями

Это отдельно стоит учесть при проектировании, чтобы не переделывать потом:

- **`Product` JSON-LD** (см. пункт 4 предыдущего SEO-гайда) должен генерироваться **автоматически** из полей товара в БД (`name`, `price`, `sku`, `image`) при рендере `catalog.php`, а не вписываться вручную в HTML. Тогда любое обновление цены клиентом в админке сразу подтянется и в структурированные данные — цена в разметке никогда не разъедется с ценой на экране.
- Аналогично **`Article` JSON-LD** для каждой статьи — `dateModified` должен автоматически обновляться при каждом сохранении статьи в админке.
- **`BreadcrumbList`** для страницы статьи можно генерировать динамически из slug и title статьи — не нужно вписывать вручную каждый раз.

Это значит: часть работы над админкой одновременно закрывает и часть SEO-долга — их стоит проектировать вместе, а не как два отдельных проекта.

## 5. Безопасность — обязательный минимум

Админка = новая точка входа для взлома. Без этого не запускать в продакшн:

- **Авторизация**: логин + пароль (хешированный, `password_hash()` в PHP), никакого хранения паролей в открытом виде.
- **Ограничение попыток входа** (rate limiting) — защита от подбора пароля.
- **CSRF-токены** на всех формах изменения данных.
- **Валидация и очистка загружаемых файлов**: проверять реальный MIME-тип картинки (не доверять расширению файла), ограничивать размер, хранить загрузки вне публично исполняемой директории или с запретом исполнения скриптов в этой папке.
- **Экранирование пользовательского ввода** при выводе на сайт (особенно поле `body_html` от WYSIWYG-редактора — прогонять через HTML-санитайзер вроде HTML Purifier для PHP, чтобы клиент не мог случайно/специально вставить вредоносный скрипт).
- Админ-панель должна быть на отдельном пути (`/admin/`), закрытом от индексации в `robots.txt` (`Disallow: /admin/`), и желательно с HTTPS принудительно.

## 6. Рекомендуемый порядок разработки

1. Спроектировать и создать таблицы `articles` и `products` в SQLite.
2. Мигрировать текущий хардкод из `catalog.html` и `articles.html`/`guide.html` в БД — написать одноразовый скрипт-миграцию, который парсит существующий HTML и заполняет таблицы (чтобы не вбивать всё вручную).
3. Переписать `catalog.php` и `articles.php`/`guide.php` так, чтобы они рендерили карточки **из БД**, а не из статичного HTML — визуально страница должна остаться идентичной.
4. Встроить генерацию `Product`/`Article`/`BreadcrumbList` JSON-LD в те же шаблоны, на основе данных из БД (см. пункт 4).
5. Сделать защищённый раздел `/admin/` с логином.
6. Реализовать CRUD-экраны: список статей → форма редактирования; список товаров → форма редактирования.
7. Подключить WYSIWYG-редактор для тела статьи.
8. Настроить загрузку и валидацию изображений.
9. Протестировать: клиент должен суметь добавить новый товар и опубликовать новую статью самостоятельно, без разработчика, и увидеть изменения сразу на сайте.
10. Закрыть `/admin/` от индексации и провести базовый аудит безопасности (проверить формы на CSRF, попробовать залить не-картинку под видом картинки и т.д.) перед сдачей клиенту.

## 7. Что важно объяснить клиенту при сдаче

- Как разница между "черновик" и "опубликовано" — чтобы можно было готовить статью заранее, не показывая её на сайте.
- Что редактор поддерживает не любое форматирование — только то, что заложено в дизайн (иначе есть риск, что клиент вставит текст из Word с непонятными стилями, и вёрстка статьи "поедет").
- Как менять порядок карточек в каталоге.
- Что для новых фото лучше сразу присылать оптимизированные `.webp`-файлы (как уже используется на сайте) — если админка не делает автоматическое сжатие/конвертацию, это стоит либо добавить в саму систему (автоконвертация загруженных JPG/PNG в WebP на лету), либо явно проговорить клиенту.
